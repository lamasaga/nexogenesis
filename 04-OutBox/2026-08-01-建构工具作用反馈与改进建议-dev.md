# 建构过程工具作用反馈与改进建议

> 日期：2026-08-01  
> 场景：对曼昆第01–20章 digest 后的约 63 张 Card 做首轮 `/construct`  
> 已完成：`diagnose` → `cluster`（拆 domain + 重挂）→ `distinguish`（人力资本之争 involves 归位）  
> 未做：`articulate`（自动枢纽建议噪声过大）、`cross_source`、`--apply-seed-links`（本轮 0 可补边）  
> 性质：过程反馈与工程/提示词建议（非 Card；默认不作已定结论）  
> 关联：`04-OutBox/2026-08-01-单domain过载-工程与提示词改进.md`；`.agent/skills/nexo-construct/SKILL.md`

## 1. 一句话结论

　　本轮建构真正创造价值的是 **cluster（归属与领域粒度）** 和 **distinguish（张力两造归位）**；诊断报告与 `structure-ops-draft` 有用但 **articulate 自动枢纽建议噪声过大**，若不经人工过滤会把建构拖回「第二次消化」。seed-links 在本库已几乎无空边，不应被当成完成态。整体工具链「能诊断、能写入」，但 **缺 domain 健康度信号、缺停用词过滤、缺「重挂 domains」的一等公民操作**。

## 2. 本轮实际路径（压缩）

| 步骤 | 工具/命令 | 结果 |
|---|---|---|
| 1 | `construct --root .` | 生成 `lenses-report.md`、`structure-ops-draft.md`、`structure-ops-llm.yaml`；seed-links = 0 |

## 3. 各类型工具：作用、本轮表现、反馈

### 3.1 诊断入口：`construct`（默认 / `--diagnose`）

**设计作用**  
　　通盘扫描卡片网，产出可读报告 + 可执行行动单 + 建议镜头顺序，避免「不做诊断直接 apply」。

**本轮表现**  
　　成功暴露结构性事实：全库实例 `domains` 几乎全是「市场效率与政策干预」；conflict involves 表面「齐全」（数量上 0 待补），但未区分 **语义是否为真两造**。行动单建议顺序 `seed-links → distinguish → articulate` 偏模板，**未把「过载 domain」抬到第一优先级**——该判断主要靠人工对照先前 OutBox。

**反馈**  
- 有价值：目录快照、conflict/枢纽候选的机器可读草稿。  
- 不足：诊断「政治」仍偏图论局部信号，弱于领域粒度与主题漂移。  

**建议**  
- 在 `lenses-report` / `structure-ops-draft` 增加 **Domain 健康度** 段：每域挂靠数、`relations` 数、body 字符、是否 `domain_overloaded`。  
- 建议镜头顺序在过载时改为：`cluster（归属/分裂）→ distinguish → articulate`。  
- 对「conflict 已有 involves」再跑一层：involves 目标是否为 claim/model 且成对对立（否则标 `involves_semantic_weak`）。

---

### 3.2 确定性补边：`--apply-seed-links`

**设计作用**  
　　无 outgoing relations 的卡自动 `applies-to` 所属 domain；低成本补空边。

**本轮表现**  
　　**0 writes**——库内几乎没有「空 relations」卡。工具正确空转。

**反馈**  
　　有用但边界清晰：只解决「孤儿边」，不解决「挂错域 / hub 边过多」。本轮若误把 seed-links 当完成态，会完全错过真问题。

**建议**  
- 报告中显式写：「seed-links=0 不代表结构健康」。  
- 增加对称操作设想：`prune-hub-applies-to`（domain relations>12 时建议裁剪），与 seed-links 成对。

---

### 3.3 镜头：`cluster`

**设计作用（契约）**  
　　假 domain、空壳领域、孤儿、domains 漂移、近义卡合并 → 归属调整 / superseded。

**本轮表现**  
　　**主价值镜头。** 将 1 张过载 domain 拆为 5 张（微观分析基础 / 市场效率与政策干预 / 企业与市场结构 / 要素与收入分配 / 贸易与相互依存），并重挂全部实例。写入后 warning 清零。  
　　缺口：Harness **没有**「批量改 domains 字段」的专用 op；本轮靠脚本生成完整 `write --batch`（保留 body、改 frontmatter）。可行，但重、易错，且不在 skill 标准流程里。

**反馈**  
- cluster 的语义定义与本库最大痛点对齐，应作为 digest 后首轮默认主镜。  
- 「原则上不新建」与「缺领域枢纽必须新建 sibling domain」需在 prompt 里写死判定，否则 Agent 会不敢拆。

**建议**  
- `construct.txt` cluster 段增加：**过载 domain → 允许新建 ≤N 张 sibling domain（须 operation 解释）+ 批量 rehome**。  
- 工程上增加 `target: card` 的轻量模式或 `op: rehome_domains`（只改 domains/relations，不必重写 body），降低 60+ 卡重挂成本。  
- 合并近义卡本轮未做；可留第二轮 cluster，且须「主卡可读 + superseded_by」，禁止只改 frontmatter 假装合并。

---

### 3.4 镜头：`distinguish`

**设计作用**  
　　张力升格、conflicts-with 无 conflict、conflict 缺 involves、主张 vs 可外核事实。

**本轮表现**  
　　机器信号「待补 involves = 0」**漏掉语义错误**：`人力资本与信号论之争` 的 involves 挂在「机会成本边际与激励」「实证分析与规范判断之分」（工具 method），而非对立 claim。人工 distinguish 后新建两造 claim 并改挂，结构才正确。

**反馈**  
　　distinguish 对「有没有 involves」敏感，对「involves 是不是两造」钝感。数量闸门 ≠ 语义闸门。

**建议**  
- 硬校验/警告：conflict 的 involves 目标不得为 method（除非特例）；优先 claim，其次对立 model。  
- 若 involves ≥3 且类型混杂（如反垄断 conflict 挂多模型），标 `conflict_hub_bloated`，建议拆两造 claim 或收窄 involves。  
- prompt 明确：distinguish **可以**为既有 conflict 补两造 claim（计入结构单元，须说明），这不算「第二次消化」。

---

### 3.5 镜头：`articulate`

**设计作用**  
　　关系团抽 model/method、entity 枢纽、补 based-on/supports；少建碎 claim。

**本轮表现（自动建议）**  
　　`structure-ops-draft` §2 列出约 12 个「枢纽概念候选」，算法是：同 domain 内标题高频词 + 尚无同名卡 → 建议升格。产出包括「贸易」「市场」「竞争」「价格」等尚可讨论项，也包含 **「经济」「之争」「政策」** 等停用词级噪声。在未拆 domain 前，噪声被单一 hub 放大。

**反馈**  
　　articulate **作为镜头有价值**，但 **当前自动候选生成器不适合直接驱动 batch**。本轮跳过是正确的工程判断，不是否定镜头本身。

**建议**  
- 停用词表：经济、市场、之争、政策、收入、成本…（可配置）。  
- 按 **拆后的多 domain 分别** 统计高频术语。  
- 候选须附「建议挂到已有哪张 model」优先于「新建 entity」。  
- Agent 规程：articulate 自动列表默认 **只读**；入 batch 前人工勾选 ≤K 条。

---

### 3.6 镜头：`cross_source`

**设计作用**  
　　多源互补/对立 → 跨源边、conflict、问题清单。

**本轮表现**  
　　未跑。本库目前几乎单教材源，跨源信号弱；优先做完领域分裂更合理。

**建议**  
　　在多文档 ingest 后再作为默认后镜；单源阶段可降级为「同书跨章桥接」（例如贸易↔要素、寡头↔自由贸易论据），避免空转。

---

### 3.7 写入闸门：`construct --apply` / `write --batch`

**设计作用**  
　　统一事务写入、校验、Journal；禁止直接改卡文件。

**本轮表现**  
　　cluster 67 writes、distinguish 3 writes 均成功。校验能抓住幽灵链接与 involves 用错类型，但对「domains 全挂同一张」无预警（已在拆分后自然消失）。

**建议**  
- validate 增加 soft warning：`domain_member_count > 25` 或单 domain 占比 > 80%。  
- construct apply 标记大量 Buffer `constructed` 的策略需文档化（本轮 cluster 曾标记大量 buffer）——避免与 digest `digested` 语义混淆，或改为仅标记 `operation.consumed_buffers`。

---

### 3.8 辅助产物：`lenses-report` / `structure-ops-draft` / `structure-ops-llm.yaml`

**设计作用**  
　　人机共用的病情单与机器可读 ops。

**本轮表现**  
　　`lenses-report` 体量极大（含全目录 + Buffer 索引），利于检索、不利于「一眼决策」。`structure-ops-draft` 的 §0/§1 清晰，§2 articulate 噪声需隔离阅读。

**建议**  
- 报告顶部增加 **Executive 摘要**（10 行内）：domain 数、过载告警、conflict 语义告警、建议镜头。  
- articulate 候选单独文件 `hub-candidates.md`，并标注 score / 停用词过滤后结果。

## 4. 工具价值排序（对本轮）

| 优先级 | 工具 | 对本轮贡献 |
|---|---|---|
| P0 | `cluster` + write batch（含破例新建 sibling domain） | 解决单 domain 过载，结构可导航 |
| P0 | `distinguish`（语义 involves，非仅计数） | 修正假两造，张力可推理 |
| P1 | `construct` 诊断报告 | 提供盘点；需加强 domain/语义信号 |
| P2 | `--apply-seed-links` | 本轮无增量；防空边仍有长期价值 |
| P2 | `articulate` 镜头（人工策展后） | 潜在补枢纽；自动列表暂不可信 |
| P3 | `cross_source` | 单源库延后 |

## 5. 改进建议汇总（可进活契约）

### 5.1 Harness

1. Domain 健康度写入 diagnose 与 `--plan` 类输出。  
2. conflict involves 语义检查（类型、数量、是否两造）。  
3. articulate 停用词 + 分 domain 统计；候选默认不自动入 batch。  
4. 支持轻量 `rehome_domains` / 批量改 frontmatter，避免整卡重写。  
5. 明确 Buffer `constructed` 标记规则，避免误伤。  

### 5.2 提示词（`construct.txt` / skill）

1. digest 后首轮：**cluster 优先于 articulate**。  
2. 写明：过载 domain 允许新建 sibling（≤N）并必须重挂。  
3. distinguish：involves 不得挂通用 method；可破例建两造 claim。  
4. articulate：自动候选只读，须勾选后写入。  
5. seed-links：完成态反模式写进 Anti-patterns（skill 已有，报告里再强调一次）。  

### 5.3 编排习惯（Agent）

1. 先读 `structure-ops-draft` 的 §0/§1 与 domain 目录，再决定镜头。  
2. 不把 articulate 高频词列表当任务清单。  
3. cluster 重挂后立刻 `Store.validate()`，确认 0 error 再进下一镜。  
4. 每镜 operation.note 写清：发现了什么、为何新建/不新建、跳过了什么。

## 7. 结语

　　建构工具链的主职应是 **通盘结构**，不是再消化一遍 Buffer。本轮证明：在正确镜头下（cluster + 语义向 distinguish），工具能把「可检索的卡堆」推进到「可导航的领域网」。短板不在「有没有 articulate」，而在 **自动信号与真结构问题的对齐**——把 domain 粒度、involves 语义、停用词过滤做进 Harness 与提示词后，建构才能从「靠 Agent 经验」变成「默认走对路」。
