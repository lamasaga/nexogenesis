# 智构涌现（Nexogenesis）介绍

> 版本：2026-07-24  
> 对应项目：`NexogenesisV0.1/`

---

## 一、简介

**智构涌现（Nexogenesis）** 是一个面向个人或学派的新一代**知识-思维涌现系统**。它的核心目标不是做传统的“笔记管理软件”，而是充当一个**思维对话智能体**：通过与人的持续对话，把零散的想法、阅读材料、争论与反思沉淀为结构化的知识图谱，并在此基础上支持分析、判断、反思与涌现。

你可以把它理解为：

- 一个以 **Markdown + Git** 为唯一事实源的本地知识底座；
- 一个由代码强制过程拓扑、由大模型负责语义判断的 **Harness 框架**；
- 一套从“对话捕获”到“文档摄入”再到“结构整理”的渐进式工作流。

智构涌现目前处于 **V0.1 → V0.2** 阶段：P0 的对话-捕获-回答闭环已经实现，P1 的文档摄入流水线（compile/digest/construct）已经完成，P2 及以后将逐步引入完整编排层、图检索/向量索引与 Web 界面。

---

## 二、为什么需要智构涌现？

传统的知识管理工具往往陷入两种极端：

1. **太轻**：纯笔记或标签系统，只有内容堆积，没有结构，越用越乱；
2. **太重**：复杂的本体论、强制模板、自动化流水线， friction 过高，最终 abandoned。

智构涌现从过去多个版本（v3.1/v3.3/v4.0/v1.1）的真实使用中总结出两条经验：

- **领域卡片是骨架**：知识网络的组织方式不是文件夹，而是“领域”这一思想空间；
- **复杂度必须有证据**：任何新增机制都必须说明它解决的真实摩擦、最小改动、有效判断标准和撤回方式。

因此，智构涌现选择了一条“务实裁剪”的路线：保留已被验证有效的机制（来源纪律、冲突一等公民、渐进式阅读、链接治理），砍掉华而不实的装饰字段和过度自动化，优先降低“高质量内容进入底座”的摩擦。

## 三、核心原则

### 3.1 底座主权不变量

`markdown + git` 是唯一事实之源。任何时候删掉全部代码、索引、数据库，只保留 `markdown + git`，系统信息零损失。图谱、向量索引、关系数据库都是**可重建索引**，永不持有不可替代的信息。

### 3.2 Harness 负责过程，LLM 负责语义

- **Harness（代码）**：强制过程拓扑——统一写入入口、schema 校验、权限检查、生成索引视图；
- **LLM（语义）**：判断内容好坏、识别冲突、生成卡片、组织论证。

Harness 不替代语义判断，语义判断不依赖“自觉”。

### 3.3 写入统一入口

任何对底座的实质写入（新建/修改卡片、更新 Profile、追加 Journal）都必须通过 `nexogenesis write --batch` 完成。禁止 AI 或用户绕过该入口直接改文件。

### 3.4 写路径优先

历代最大瓶颈不是检索，而是**策展成本**——如何让高质量内容低摩擦地进入底座。智构涌现的每个机制都优先服务于写路径。

### 3.5 复杂度必须有证据

任何新增机制必须回答四个问题：

1. 它解决什么真实摩擦？
2. 最小改动是什么？
3. 怎么判断有效？
4. 怎么撤回？

## 四、系统架构

```text
┌─────────────────────────────────────────────────────────────┐

├─────────────────────────────────────────────────────────────┤
│ 底座：markdown + git = 唯一事实之源                          │
└─────────────────────────────────────────────────────────────┘
```

## 五、目录与存储结构

```text
AGENTS.md                    # 系统手册（运行时契约）
README.md                    # 项目说明
00-Inbox/                    # 待处理原始材料
01-Cards/                    # 知识卡片（扁平存储）
   ├── _meta/                 # 自动生成的 ontology / 索引视图
   └── <id>.md               # 所有卡片平铺
02-Profile/                  # 用户/学派思想档案 + 问题清单
03-Archive/                  # 已处理原始材料
04-OutBox/                   # 分析产物、回答、报告
05-Buffer/                   # compile 产出的原子化片段
06-Journal/                  # 操作大事记
nexogenesis/                 # Python 包（Harness 实现）
schemes/default/             # 默认沉淀方案（含 prompt 模板）
hooks/                       # git hooks
```

关键变化：`01-Cards/` 扁平化，不再按领域分子目录；领域归属由 frontmatter 的 `domains` 字段显式声明。

## 六、卡片系统

### 6.1 7 种卡片类型

| 类型 | 回答的问题 | 最小内容要求 |
|---|---|---|
| `domain` | 这是哪个思想领域？ | 核心问题、边界、内在张力 |
| `claim` | 主张/立场是什么？ | 一句话主张、依据、已知限制 |
| `phenomenon` | 发生了什么模式？ | 模式描述、典型实例、反例 |
| `model` | 怎么理解这个复杂事物？ | 核心思想、关键组件、因果/结构、失效边界 |
| `method` | 怎么做？ | 输入、步骤、输出、适用边界 |
| `entity` | 这个对象是什么？ | 定义、关键属性、来源 |
| `conflict` | 根本矛盾在哪？ | 对立双方、核心分歧点、各自证据、调和可能 |

`question` 和 `synthesis` 不是卡片类型：问题保存在 `02-Profile/问题清单.md`；synthesis 是 `04-OutBox/` 中的回答产物，若可复用再拆成卡片。

### 6.2 核心 frontmatter

```yaml
---
id: "cognitive-scaffolding"
title: "认知脚手架"
type: "model"
maturity: "growing"              # seed | growing | mature
lifecycle: "active"              # active | superseded | archived
domains: ["teaching", "cognitive"]
origin: "document"               # user | system | document | external
sources:
  - "《心智的构建》第 4 章"
relations:
  - target: "zone-of-proximal-development"
    type: "based-on"
    note: "脚手架作用在最近发展区内"
created: "2026-07-01"
updated: "2026-07-24"
theory_status: "active"          # 可选：draft | active | dormant
---
```

### 6.3 8 种关系

`extends`、`supports`、`conflicts-with`、`involves`、`example-of`、`applies-to`、`based-on`、`influences`。

领域归属不是关系，由 `domains` 字段声明；冲突参与由 `involves` 反向生成视图。

## 七、工作流

### 7.1 P0：对话-捕获-回答闭环

```text
用户提问
  → /talk：轻量入场 + 直接回答
  → 对话结束：/capture 提出 ≤3 个候选
  → 用户批准/修改/驳回
  → AI 生成 batch 文件
  → nexogenesis write --batch
       → 临时写入 → 校验 → 原子提交 → Journal → 索引
  → 后续 /answer 检索复用
```

### 7.2 P1：文档摄入流水线

```text
00-Inbox/ 原始文档
  → /compile  → 05-Buffer/ 原子片段
  → /digest   → 01-Cards/ 卡片 + 02-Profile/ 问题
  → /construct→ 01-Cards/ 领域调整 + 关系补全 + Profile 更新
```

P1 不直接调用 LLM API，而是由 Harness 生成 prompt/batch，由 code agent 调用 LLM 并把结果回写，再 `--apply` 完成落地。未来可通过 `LLMClient` 接口切换为自动调用。

## 八、Harness CLI

```bash
python -m nexogenesis init                  # 初始化项目结构，安装 git hook
python -m nexogenesis validate              # 校验 frontmatter、链接、orphan
python -m nexogenesis index                 # 生成领域/冲突/理论视图
python -m nexogenesis write --batch <file>  # 统一原子写入入口
python -m nexogenesis doctor                # 一致性检查与诊断
python -m nexogenesis migrate --to <scheme> --dry-run  # scheme 迁移预演
python -m nexogenesis compile [--apply]     # 文档编译
python -m nexogenesis digest [--apply]      # Buffer 消化
python -m nexogenesis construct [--apply]   # 结构整理
```

---

## 九、沉淀方案层（Scheme）

“如何沉淀和结构化”是一种可替换的策略。默认方案 `schemes/default/` 是 v4.0 优化版，包含：

- `scheme.md`：方案说明；
- `ontology-template.md`：启用时生成的 `_meta/ontology.md` 模板；
- `profile-template.md`：Profile 档案模板；
- `prompts/*.txt`：各体裁 compile 与 digest/construct 的 Jinja2 prompt 模板；
- `migration.md`：scheme 迁移规则。

未来可以按语料类型、建模对象替换为不同 scheme。

## 十、当前状态与路线图

### 已完成

- P0：对话-捕获-回答闭环、统一 CLI、原子写入、索引、Journal、doctor、migrate dry-run；
- P1：compile/digest/construct 文档摄入流水线、Jinja2 prompt 模板、37 项测试。

### 延后机制（进入条件）

| 机制 | 进入条件 |
|---|---|
| 更多文档摄入自动化 | 当前手动 Agent 模式成为主要瓶颈 |
| 图检索/向量库 | 文本检索在真实规模下明显失效 |
| Web 界面 | 文件与 code agent 成为主要使用障碍 |
| 多 Agent 分工 | 单流程出现可测的并发/隔离/专业化需求 |
| 联邦交换 | 至少两个真实用户需要交换结构化思想 |

## 十一、如何开始使用

```bash
cd NexogenesisV0.1
python -m venv .venv
.venv\Scripts\pip install -e ".[dev]"
python -m nexogenesis init
python -m nexogenesis validate
python -m nexogenesis index
```

之后即可开始对话，或用 `compile` 摄入文档。
