## 〇、总坐标系：一个 agent 系统有四个可被优化的层面

当下所有 agent 技术，本质都在优化以下四层中的某一层。分清层，才能看清每项技术的边界：

| 层           | 优化对象                                   | 代表技术                        | 改变它的成本          | 效果半衰期    |
| ----------- | -------------------------------------- | --------------------------- | --------------- | -------- |
| **L1 权重层**  | 模型参数本身                                 | RLVR、agentic RL、SFT         | 极高（GPU、数据、训练工程） | 长        |
| **L2 工件层**  | prompt、SKILL.md、AGENTS.md、rubric 等文本工件 | SkillOpt、DSPy、GEPA、TextGrad | 中（离线优化循环）       | 中        |
| **L3 上下文层** | 每次调用时喂给模型的信息组装                         | Context engineering、RAG、压缩  | 低               | 短（随任务波动） |
| **L4 环境层**  | 工具、循环结构、验证器、状态外置                       | Harness / Loop 工程           | 中低（工程改造）        | 长        |
|             |                                        |                             |                 |          |

两个关键判断：
- **行业演进方向是 L3→L4→L2**：prompt 工程（2022–24）→ context 工程（2025）→ harness 工程（2026）→ skill 训练（2026 中，SkillOpt 是标志性工作）。越往 L4/L2 走，杠杆越大。
- **ETP v1.0 的全部资产都在 L2 层**（AGENTS.md 就是一份巨型手工 skill），但它的闭环目前靠 L4 层的"纪律"而非"机械强制"维持。**SkillOpt 恰好证明了：L2 层工件可以用 L1 层的训练纪律来优化**——这就是对接点（§四、§五）。

## 一、ETP 项目技术解构：我们现在手里有什么

### 1.1 ETP 的技术本质

剥开术语，ETP v1.0 由四种技术成分构成：

| 成分       | 对应工业界概念                            | ETP 实现                               |
| -------- | ---------------------------------- | ------------------------------------ |
| 自然语言程序   | prompt 程序 / skill 文档               | AGENTS.md（指令集即程序，LLM 即解释器）           |
| 文件系统状态   | state externalization（Ralph 模式的核心） | markdown + git（一切状态外置于文件）            |
| 渐进式上下文组装 | context engineering（Select 策略）     | ontology → domains → instances 的渐进阅读 |
| 纪律驱动闭环   | 未机械强制的 harness                     | 五条强制回路 + 脱钩指标（靠 agent 自觉）            |

### 1.2 ETP 已经"预见"了哪些行业共识

回看 2026 年的 harness 工程文献，ETP 在设计阶段独立得出了几个后来被验证的判断，值得记录：

1. **状态外置优于上下文记忆**——Ralph 模式（Geoffrey Huntley 提出，两个月 12k stars）的核心是"每轮迭代重启干净上下文，状态活在 git 和 progress.txt 里"。ETP 的 markdown 底座 + 操作日志与此同构。
2. **给地图，不给一千页手册**——OpenAI Codex 团队 harness 工程的第三条原则"渐进披露"（agent 按需找信息，而非一次性灌入）。ETP 的渐进式阅读就是知识库场景的渐进披露。
3. **机械强制优于文档规劝**——Codex 团队发现"写在文档里的'请用这个模式'会被忽略，于是造了自定义 linter"。这正是 ETP §九"诚实版 hooks"的逻辑，也是 V0.5"虚构基建"教训的行业版。
4. **可验证的终止条件**——loop 工程的第一原则（"让测试通过"是好目标，"改进代码"是坏目标）。ETP 的脱钩指标就是试图给"思考"这种模糊目标装上可验证的仪表。

### 1.3 ETP 的核心缺口（用坐标系语言重述）

- **L4 缺口**：闭环无机械强制（赌注 1，已知）；
- **L2 缺口**：AGENTS.md 的演化靠"手写修订"，没有**优化器**——没有批次、没有学习率、没有验证门控。SkillOpt 的出现证明这个缺口可以被工程化填平（§四）；
- **L1 缺口**：暂无权重层手段（短期不需要，远期用于本地小模型工人，§六）。

## 二、Loop 工程（Harness 工程）：当下实现方式

### 2.1 三时代演进

```
Prompt Engineering（2022–24）：写好一段话
  → Context Engineering（2025 中）：组装好每次调用的信息（Anthropic: Write/Select/Compress/Isolate）
  → Harness Engineering（2026）：设计 agent 栖居的整个环境（工具、循环、验证、约束）
```

行业共识（OpenAI、Anthropic、LangChain 多源验证）：**"Agent 不难，Harness 难"**。同一模型同一 prompt，仅换运行环境，编程基准成功率可从 42% 跳到 78%。给 agent 加上约束（规则、反馈环、linter），生产力不降反升——约束缩小了搜索空间。

### 2.2 一个良好 loop 的解剖（2026 年工业标准）

| 组件 | 要求 | ETP 对照 |
|---|---|---|
| 目标 | 有可测试的终止条件 | 脱钩指标给了"思考"可测的仪表 ✅ |
| 工具 | 触及真实环境，反馈诚实 | 目前是文件读写；缺执行类工具 ⚠️ |
| 上下文管理 | 摘要、剪枝、状态外置 | 渐进阅读 ✅ ；无自动压缩 ⚠️ |
| 终止与升级 | 显式成功/失败出口 + 卡死时升级给人 | 审批收件箱 ✅ ；无卡死检测 ⚠️ |
| 错误分类 | 可恢复（测试失败=反馈）vs 致命（凭证缺失=硬停） | 未定义 ❌ |

### 2.3 四条被反复验证的工程原则

1. **KV-cache 命中率是生产环境最重要的指标**（Manus 团队，四次重写框架后的结论）：prompt 前缀稳定性 > prompt "质量"；不要中途换工具列表；harness 要设计成换模型也能活。**对 ETP 的启示**：入场协议的上下文组装应保持稳定前缀（ontology + 问题清单 + 透镜定义固定在前，变量内容在后）。
2. **机械强制 > 文档规劝**（OpenAI Codex：五个月、零人工代码、约 100 万行生成代码、约 1500 个 PR）：知识系统化进仓库 + linter 强制架构规则 + 渐进披露。**对 ETP**：P0 脚本不是可选项，是闭环的地基。
3. **生成者/评估者分离**（Anthropic：模型不能可靠评估自己的工作，需要 GAN 式的 Generator/Evaluator 分工）：**对 ETP**：判断引擎的透镜独立解读纪律（§6.2）已是此原则；反思器官与执行器官的分离也是。SkillOpt 的 target/optimizer 非对称架构再次印证（§四）。
4. **Agent 可以改进自己的 harness**（agentic flywheel，LangChain 案例：只改 harness 不改模型，指标 52.8%→66.5%）：**对 ETP**：/evolve 就是 ETP 的 flywheel——但目前是手动的。

### 2.4 小结

ETP 在 loop 工程上的概念完备度出乎意料地高（闭环、指标、审批、状态外置都有），**缺的是把"纪律"变成"机械"的那一层代码**。这不需要新设计，只需要执行 §九的 P0–P2 清单。

## 三、大模型强化学习：当下实现方式

### 3.1 技术谱系（2022 → 2026）

```
RLHF（InstructGPT, 2022）：人类偏好 → 奖励模型 → PPO
  → RLVR（DeepSeek-R1, 2025-01）：可验证奖励（数学/代码对错），规则化 reward，GRPO 崛起
  → GRPO 家族（2025）：GRPO → DAPO（clip-higher、动态采样）→ Dr.GRPO（去长度偏置）→ GSPO / RLOO / GiGPO / ARPO
  → Agentic RL / ARLT（2025–26）：多轮、长程、工具交互中的 RL
```

**GRPO 的核心思想**（理解后续一切的基础）：同一问题采样一组回答，组内相对比较优势（advantage），不需要训练单独的 value model——用"组内排名"替代"绝对打分"。这让 RL 在 LLM 上变得便宜且稳定。

### 3.2 Agentic RL 的三个硬问题与当前解法

| 硬问题 | 说明 | 当前解法 |
|---|---|---|
| **信用分配** | 50 步轨迹里哪一步导致了最终成败？ | LightningRL：轨迹分解为 transition，先分配回合回报到各动作，再在动作内做 token 级优化（兼容 GRPO/PPO）；ARLT：在工具调用级别分配信用 |
| **奖励稀疏** | 只有终局对错，中间步骤无信号 | AIR（Agent Lightning 的自动中间奖励：把监控信号如工具调用成败转为中间奖励）；过程奖励模型 PRM；rubric 化奖励 |
| **长程不稳** | 轨迹长、上下文累积、训练易崩 | transition 级数据组织（避免整轨迹拼接+掩码）；轨迹过滤；异步容错执行器 |

### 3.3 奖励工程：思想模拟器最该关注的前沿

RLVR 的前提是"奖励可验证"（数学有答案、代码能跑）。**思想质量没有 ground truth**——这是把 RL 引入思想模拟器的根本障碍。但 2026 年的奖励工程给出了三条桥：

1. **Rubric 作为训练信号**：RIFL（微调 rubric 验证器）、VerIF（规则+LLM 混合验证）、RLCF（从指令提取检查清单）、ToolRL（细粒度工具使用奖励）。ETP 的价值三维（生成力/解释力/可行动性）可以 rubric 化为逐条原子检查项。
2. **LLM-as-judge 的可靠性工程**：2026 年测量学研究显示——清晰的评分标准比 chain-of-thought 更能提升 judge 可靠性；单次评分不可靠，需要逐条原子评分 + 集成评判 + 心理测量学信度指标（Autorubric 框架）。**判断引擎的 rubric 设计必须按这个标准做**。
3. **真实部署数据**：对 86 名从业者的调查显示 68% 的线上 agent 在人介入前执行不超过 10 步——长程自主性仍是部署与基准之间的鸿沟。思想模拟器的"长程"体现在跨会话的月级演化，而非单会话步数，这是另一个问题形状。

### 3.4 Microsoft Agent Lightning：权重侧的对接候选

微软研究院 2025-08 发布（arXiv 2508.03680，2025-10 开源），是目前"给任意 agent 加 RL"最完整的框架：

- **核心创新：训练-执行解耦（TA Disaggregation）**。agent 代码几乎不改（LangChain/AutoGen/Claude Agent SDK/裸 Python 均可），通过 OpenTelemetry 或轻量钩子采集轨迹；
- **建模**：agent 执行 = POMDP，状态 = 语义变量快照，动作 = 一次 LLM 调用，奖励 = 中间或终局标量；
- **LightningRL**：层次化信用分配（先分配到动作，再动作内 token 优化），兼容 GRPO/PPO；
- **选择性优化**：多 agent 系统中只训练指定 agent；
- **多种优化模式**：RL、自动 prompt 优化、SFT；
- **现实约束**：仅 Linux + CUDA（RTX 4090 级）可完整训练；Windows/Mac 不可用。

**对 ETP 的定位**：Agent Lightning 是 L1（权重层）方案。对思想模拟器，它短期过重（需要 GPU、可验证奖励、任务集），但有两个概念值得现在吸收：①**POMDP 化**——ETP 的底座快照即状态、LLM 调用即动作、脱钩指标即奖励，这个形式化日后直接可用；②**选择性优化**——未来只训练"工人 agent"（编纂/馆员用本地小模型），前台保持大模型 API。

## 四、微软 SkillOpt：用训练大模型的手段训练 skill

> 这是用户点名分析的工作，也是与 ETP 对接价值最高的一项。2026-06 发布（微软 + 上交大/同济/复旦），开源：github.com/microsoft/SkillOpt。

### 4.1 它解决的问题

当前 skill（SKILL.md 类文本工件）的生产方式极其粗糙：人工手写一版、或 LLM 单次生成、或失败后零散追加经验——**这是"写文档"，不是"训练能力"**。SkillOpt 的主张：训练大模型时没人指望一次前向传播收敛，skill 也不该指望一次写好。把深度学习的整套训练纪律映射到文本空间。

### 4.2 核心映射表（不是隐喻，是系统设计）

| 深度学习 | SkillOpt 文本空间对应 |
|---|---|
| 参数 | 纯文本技能文档（部署形态 `best_skill.md`） |
| 前向传播 | 目标模型持当前 skill 在训练集上跑一个 rollout 批次，记录完整轨迹 |
| 梯度方向 | 基于轨迹的编辑方向（成功驱动的编辑 + 失败驱动的编辑） |
| 学习率 | **编辑预算**：单步允许的最大修改次数（余弦衰减调度：前期大改、后期微调） |
| 优化器 | 独立的**优化器模型**（离线运行），目标模型与 harness **完全冻结** |
| Batch / 累积 | rollout 批次大小控制更新噪声；支持多批独立反思后合并（累积机制） |
| 验证集 | **保留选择门**（held-out selection gate）：候选 skill 得分必须**严格大于**当前分才接受，平局也拒绝 |
| 训练日志 | **元技能**（meta-skill）：记录哪些编辑模式有效/被拒，只存在于优化器侧，**永不部署** |
| 正则化 | 拒绝缓冲区 + 分层合并（"失败纠正"优先级最高） |
| 长期记忆 | 慢速更新：每个 epoch 末对比前后 skill 在相同样本上的表现，纵向经验写入标记保护区 |

### 4.3 实验结果（为什么这项工作值得认真对待）

- 6 个基准 × 7 款模型 × 3 种框架 = 52 个评估单元，**52 项全部最优或并列最优**；GPT-5.5 直接对话场景平均 +23.5；
- 击败人类专家编写、one-shot 生成、TextGrad、GEPA、EvoSkill 等全部基线，领先最强对手平均 +5.4；
- **被接受的编辑只有 1–4 次**（中位 2.5）——绝大多数提升来自极少的关键编辑；LiveMath 单次接受编辑 +29.3 分；
- 最终 skill 仅 379–1995 token（中位约 920）——**比多数业务系统提示词还短，人可在几分钟内审完**；
- **三维迁移**：跨模型（GPT-5.4→nano 仍有 +3.0~+9.4）、跨框架（Codex 训练的技能投入 Claude Code +59.7）、跨数据集——证明学到的是深层程序逻辑而非表面格式；
- 成本：程序型任务每提升 1 个绝对点约 0.6M–3.6M token，一次性开销，推理侧零额外成本。

### 4.4 深层解读：SkillOpt 真正证明了什么

1. **文本工件是可训练的"参数"**——而且训练后的工件可审计、可迁移、可版本化（权重做不到这三点）。对个人系统，这比权重训练重要得多。
2. **"训练记录"与"推理载荷"的解耦**——元技能只在优化器侧，部署的永远是精简的最佳工件。这解决了"经验越攒越多、prompt 越胀越大"的慢性病（对比 V0.5 的卡片膨胀恐惧）。
3. **严格验证门控（严格大于、平局拒绝）+ 极少接受编辑**——防止"静默漂移"的制度设计。这与 ETP 宪法层"提提案+批准"精神一致，但给出了可操作的量化判据。
4. **优化器/目标分离**——优化用的模型可以和部署用的模型不同（用前沿模型优化、小模型部署）。ETP 可以用大模型优化手册、小模型执行指令。

### 4.5 SkillOpt 与 Agent Lightning 的关系

| | SkillOpt | Agent Lightning |
|---|---|---|
| 优化对象 | 文本工件（L2） | 模型权重（L1，也支持 prompt 优化/SFT） |
| 环境要求 | 任意（纯 API 即可） | Linux + CUDA |
| 产物 | 可读、可审计、可迁移的 md | 更强但不可读的权重 |
| 适合场景 | 个人/小团队、快速迭代 | 有算力、有任务集、追求极限性能 |

前沿趋势是两者合流：Inspo（指令-策略协同进化，arXiv 2512.01945）与 ReSkill（RL 训练过程中用 Thompson 采样协同演化 skill 版本，arXiv 2606.01619）已经在做"工件与权重共同训练"。**文本与权重的协同进化是 2026 下半年的明确方向。**

## 五、对接方案：把 ETP 变成可训练的思想模拟器

这是全文的核心。目标不是给 ETP 接一个外部工具，而是**用 SkillOpt 的训练纪律重写 ETP 的反思器官，并为远期的权重层对接预留形式化接口**。

### 5.1 ETP 的"可训练参数"清单

ETP 里哪些文本工件是"参数"（可被优化器编辑）？按训练价值排序：

| 参数工件 | 内容 | 预期收益 |
|---|---|---|
| 六透镜定义 | 每个透镜的提问方式、产出格式 | 判断质量（直接影响价值评估） |
| 入场协议模板 | 上下文组装顺序、前缀稳定性设计 | 对话质量 + KV-cache 命中 |
| 蒸馏 prompt | 对话→碎片的提取指令 | 原料质量（garbage in 的源头） |
| 判断 rubric | 价值三维的逐条原子检查项 | 评估信度（LLM-as-judge 可靠性） |
| 元理论孵化 prompt | 雏形生成的触发与格式 | 理论生态质量 |
| AGENTS.md 指令章节 | 各指令的执行步骤 | 整体流程质量 |

**宪法层核心原则不是参数**——它们是超参数，只有用户能改。这个划分本身就是权限三层模型的训练化表达。

### 5.2 训练信号：思想模拟器的奖励从哪来

思想无 ground truth，但 ETP 有五个弱信号源，组合后足够：

| 信号 | 性质 | RL 类比 |
|---|---|---|
| 脱钩指标（§7.5） | 可计算、可自动 | 可验证奖励（RLVR 式） |
| 用户批准/驳回记录（蒸馏确认、理论转正、宪法提案） | 稀疏但高信度 | 偏好奖励（RLHF 式） |
| 价值轨迹（同一对象多次评估的变化） | 延迟、纵向 | 回合回报 |
| 分歧档案的后续解决情况 | 延迟、稀疏 | 长程信用 |
| 预测-验证（理论的"生成的问题"后续是否被证实有生产力） | 月级延迟 | 慢速更新信号 |

**关键工程**：把"用户批准/驳回"从一次性交互变成**结构化训练数据**——每次审批记录（提案内容、上下文指标、用户决定、用户批注）。这是思想模拟器的 RLHF 数据集，日积月累，比任何外部数据都珍贵。

### 5.3 ETP-SkillOpt 架构：训练循环与推理循环分离

```
┌──────────────── 推理循环（日常，冻结手册） ────────────────┐
│  对话 / 判断 / 蒸馏 / 摄入 —— 全部按当前 best_manual 执行    │
│  产生：轨迹（日志）、审批记录、指标、分歧档案                 │
└──────────────────────┬─────────────────────────────────────┘
                       │ 积累一个 epoch（默认 10 次会话，即现有心跳）
┌──────────────────────▼─────────────────────────────────────┐
│                训练循环（离线 epoch，优化器模式）            │
│  1. 回放本 epoch 轨迹（操作日志 + 轻反思 + 审批记录）        │
│  2. 优化器（大模型）提出手册编辑方向：成功驱动 + 失败驱动     │
│  3. 分层合并，失败纠正优先；编辑预算截断（余弦衰减）          │
│  4. 验证门控：在"回放评估集"上对比新旧手册（严格大于才接受）  │
│  5. 宪法层变更 → 用户批准（用户 = 最终 held-out gate）        │
│  6. 元技能更新：哪些编辑模式有效/被拒（仅优化器侧可见）       │
└────────────────────────────────────────────────────────────┘
```

**与现有设计的对应关系**（大部分零件已经存在）：

| SkillOpt 概念 | ETP 已有 | 需要新建 |
|---|---|---|
| rollout 批次 | 10 次会话的心跳周期 | — |
| 轨迹记录 | 操作日志 + 轻反思 | 结构化审批记录 |
| 编辑方向 | 深反思的摩擦模式分析 | 明确区分成功/失败驱动编辑 |
| 学习率/调度 | 无 | 编辑预算 + 余弦衰减（宪法层变更频率上限） |
| 验证门控 | 用户批准（定性） | **回放评估集**（定量，见下） |
| 元技能 | 06-Journal（混在运行日志里） | 独立的优化器侧状态文件 |
| best 工件 | AGENTS.md 当前版 | git tag 标记 best_manual |

**回放评估集**是唯一的全新组件：从问题清单的历史问题中选出 10–20 个有代表性的"评估任务"（带当时的上下文快照与已知的优质回答特征），候选手册与当前手册分别在这些任务上影子执行，由优化器按 rubric 打分对比。这就是思想模拟器的 held-out set——它把"用户觉得变好了"从感觉变成测量。

### 5.4 与建构主义的相容性检查

有人会问：训练 = 收敛，建构主义不是说没有真理可收敛吗？不矛盾——**ETP 训练的目标函数不是"更接近真理"，而是"更精确的定位能力"**：生成的问题是否更有生产力、失效边界的划定是否更准确、透镜分歧是否更锐利。这些是能力指标，不是真理指标。SkillOpt 优化的是"程序性知识"（先检查结构再执行验证），ETP 优化的是"思维程序"（先冲突后综合、先定位后表达）。收敛的是方法，不是结论。

### 5.5 远期：权重层对接（Agent Lightning 式）

当①本地小模型工人（编纂/馆员）上线、②回放评估集与审批数据积累到一定规模、③有 Linux+CUDA 环境时：

- ETP 的 POMDP 化：状态 = 底座快照（语义变量：当前问题、相关卡片集、手册版本），动作 = 工人 agent 的 LLM 调用，奖励 = 脱钩指标变化 + 审批通过率；
- 用 Agent Lightning 的选择性优化，只训练工人小模型（前台与优化器保持大模型 API）；
- 文本与权重协同进化（Inspo/ReSkill 路线）：手册版本与小模型权重版本联合调度——这是 AgentWeb 时代的技术形态。

## 六、路线图更新：思想模拟器的三步

在原 webagent 路线图基础上增补（原 Phase 不变，以下为强化）：

| 阶段 | 内容 | 来自本文 |
|---|---|---|
| **P1+** | P0 脚本 + **结构化审批记录**（每次批准/驳回落库） | §5.2 |
| **P2+** | 编排层 + **回放评估集**（问题清单中选 10–20 个评估任务）+ 编辑预算与调度 | §5.3 |

思想模拟器的终局形态：**一个用对话生产思维轨迹、用指标测量思维质量、用训练纪律优化自身思维程序的系统**。它模拟的不是"思想的结果"（那是知识库），而是"思想的过程"（这是可训练的思维程序）。
